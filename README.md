 # Switchyard

> Локальный оркестратор для работы с несколькими AI-ресурсами.

Если у тебя есть несколько AI API, локальные модели или другие ресурсы для запуска AI-задач, рано или поздно появляется одна и та же проблема: **куда отправить следующую задачу?**

Один ресурс быстрее, другой дешевле. У третьего закончилась квота, четвёртый временно недоступен, а пятый лучше подходит для конкретного типа задачи.

Switchyard пытается решить именно эту проблему.

Он собирает разные AI-ресурсы в единый пул и решает, какой из них использовать для конкретной задачи.

---

## Зачем это вообще нужно

Представим, что у нас есть:

```text
Claude
OpenAI
Ollama
ещё несколько ресурсов
```

У каждого из них свои характеристики:

```text
                Стоимость   Задержка   Квота   Возможности
Claude             $           ↓         80%        +++
OpenAI             $$          ↓↓        40%        +++
Ollama              0          ↓↓↓       ∞          ++
```

Если всегда использовать один и тот же ресурс, остальные фактически простаивают.

Можно, конечно, написать что-то вроде:

```text
A → B → C → A → B → C
```

Но довольно быстро становится понятно, что этого недостаточно.

Что делать, если `B` сейчас недоступен?

Что делать, если у `C` не хватает контекстного окна?

Что делать, если `A` дорогой, а текущая задача вполне может выполняться локально?

Что делать, если у одного ресурса почти закончилась квота?

И главное:

> **Как принимать это решение автоматически?**

Это и есть задача Switchyard.

---

## Что делает Switchyard

Switchyard рассматривает доступные AI-системы как набор ресурсов.

Условно:

```text
                       ┌── Claude
                       ├── OpenAI
Задача → Switchyard ───┼── Ollama
                       ├── Local API
                       └── ...
```

Перед выполнением задачи система смотрит на доступные ресурсы и отбрасывает те, которые по каким-либо причинам не подходят.

После этого scheduler выбирает наиболее подходящий вариант согласно текущей policy.

Например:

```text
Задача:
- нужна большая контекстная длина
- желательно быстро
- стоимость не критична

Resource A
✓ подходит
✓ доступен
✓ большая контекстная длина
✗ высокая задержка

Resource B
✓ подходит
✓ доступен
✓ большая контекстная длина
✓ низкая задержка

Resource C
✗ недостаточно контекста
```

Выбирается `B`.

После выполнения Switchyard получает результат и обновляет информацию о ресурсе.

Получается цикл:

```text
Задача
  ↓
Поиск подходящих ресурсов
  ↓
Выбор ресурса
  ↓
Выполнение
  ↓
Результат
  ↓
Обновление состояния
```

---

## Switchyard — это не просто API Gateway

Это важное различие.

Обычный gateway в основном занимается маршрутизацией запросов:

```text
Request → Provider → Response
```

Switchyard пытается работать уровнем выше:

```text
Workload
   ↓
Требования
   ↓
Доступные ресурсы
   ↓
Текущее состояние
   ↓
Policy
   ↓
Scheduler
   ↓
Resource
   ↓
Execution
```

То есть вопрос не только в том, **куда отправить HTTP-запрос**.

Нужно сначала определить:

> какой ресурс сейчас лучше всего подходит для этой работы?

Именно вокруг этого строится проект.

## Что такое Resource

Для Switchyard ресурс — это не просто `provider + api_key`.

У него есть состояние и характеристики.

Примерно так:

```text
Resource
├── provider
├── model
├── capabilities
├── quota
├── rate limits
├── cost
├── latency
├── health
├── priority
└── authentication
```

Например, два ресурса могут использовать одну и ту же модель, но иметь разное состояние:

```text
claude-main
├── quota: 80%
├── latency: 420 ms
└── healthy

claude-secondary
├── quota: 15%
├── latency: 250 ms
└── healthy
```

Для одного типа задачи выгоднее использовать первый, для другого — второй.

---

## Как выбирается ресурс

На первом этапе я не хочу делать какую-то магию.

Сначала будут реализованы простые стратегии, с которыми можно нормально сравнивать более сложные алгоритмы:

* Round Robin
* Least Used
* Quota Optimized
* Cost Optimized
* Latency Optimized
* Quality First
* Balanced

Например, `Cost Optimized` будет стараться минимизировать стоимость.

`Latency Optimized` — задержку.

`Quota Optimized` — эффективнее использовать доступные квоты.

`Balanced` сможет учитывать несколько факторов одновременно.

Условно:

```text
score =
    reliability
  + quality
  + quota efficiency
  - cost
  - latency
```

Конкретная формула пока не является частью спецификации. Её имеет смысл выбирать после экспериментов.

---

## Почему сначала без ML

Потому что добавлять ML просто ради того, чтобы написать «AI-powered scheduler», бессмысленно.

Сначала у нас должны быть нормальные baseline-алгоритмы.

Например:

```text
Round Robin
       ↓
Balanced
       ↓
наш scheduler
```

И для всех одинаковый набор задач.

Если окажется, что простой `Balanced` уже решает проблему достаточно хорошо, отлично.

Если окажется, что история предыдущих запросов позволяет лучше предсказывать задержку, вероятность ошибки или стоимость — тогда можно попробовать добавить predictive model.

То есть направление примерно такое:

```text
Deterministic Scheduler
          ↓
      Benchmarks
          ↓
   Где он ошибается?
          ↓
    Prediction
          ↓
 Adaptive Scheduler
```

ML здесь — инструмент, а не цель проекта.

## Что происходит при ошибке

Выбранный ресурс может упасть.

Или вернуть rate limit.

Или временно стать недоступным.

Поэтому выполнение задачи не заканчивается на выборе ресурса.

Например:

```text
Resource A
   ↓
Rate Limit
   ↓
Retry / Backoff
   ↓
не получилось
   ↓
Fallback
   ↓
Resource B
```

Но retry нужен не всегда.

Например, если запрос некорректный, бессмысленно отправлять его ещё пять раз.

Поэтому Switchyard должен различать хотя бы:

```text
temporary error
retryable error
fallbackable error
fatal error
```

---

## Состояние ресурсов

Чтобы принимать нормальные решения, Switchyard должен знать, что сейчас происходит с ресурсами.

Например:

```text
Resource       Health     Quota     Latency
------------------------------------------------
claude-main    healthy     82%       420 ms
openai-main    healthy     31%       280 ms
ollama-local  healthy      ∞         150 ms
backup         offline      0%         -
```

Часть информации может быть известна заранее из конфигурации.

Часть придётся собирать во время работы.

---

## И ещё одна важная вещь — объяснимость

Если scheduler выбрал какой-то ресурс, хочется понимать почему.

Например:

```text
$ switchyard explain last

Selected: openai-main

Почему:
✓ ресурс совместим с задачей
✓ доступен
✓ достаточная квота
✓ низкая ожидаемая задержка
✓ соответствует текущей policy

Не выбраны:

claude-main
└─ выше ожидаемая стоимость

ollama-local
└─ недостаточное контекстное окно
```

Для простой системы это может показаться мелочью.

Для scheduler, который со временем станет сложнее, это уже довольно важно.

## Архитектура

Пока проект находится на стадии проектирования, поэтому архитектура ещё может меняться.

Предварительно:

```text
src/switchyard/
├── domain/
│   ├── resource.py
│   ├── workload.py
│   ├── quota.py
│   ├── usage.py
│   └── policy.py
│
├── providers/
│   ├── base.py
│   ├── anthropic.py
│   ├── openai.py
│   └── ollama.py
│
├── routing/
│   ├── router.py
│   ├── scheduler.py
│   ├── scoring.py
│   └── policies.py
│
├── quota/
│   ├── tracker.py
│   └── predictors.py
│
├── health/
│   └── monitor.py
│
├── storage/
│   ├── database.py
│   └── repositories.py
│
├── security/
│   └── credentials.py
│
├── cli/
│   └── commands.py
│
└── application/
    └── orchestrator.py
```

Здесь есть несколько основных частей.

### `domain`

Модели предметной области:

```text
Resource
Workload
Quota
Usage
Policy
```

### `providers`

Адаптеры конкретных AI-систем.

Например:

```text
Anthropic
OpenAI
Ollama
```

### `routing`

Всё, что связано с выбором ресурса.

Здесь будут жить scheduler, scoring и policies.

### `health`

Проверка состояния ресурсов.

### `storage`

Локальное хранение состояния и истории.

### `security`

Работа с credentials.

### `cli`

Пользовательский интерфейс.

## Конфигурация

Конфигурация должна оставаться простой.

Например:

```yaml
resources:

  claude-main:
    provider: anthropic
    model: claude-sonnet

  openai-main:
    provider: openai
    model: gpt

  local:
    provider: ollama
    model: qwen

policy:
  strategy: balanced
```

При этом конфигурация не должна превращаться в место, где находится половина бизнес-логики.

## CLI

Основным интерфейсом на первых этапах будет CLI.

Например:

```bash
switchyard status
```

Показать состояние ресурсов.

```bash
switchyard resources
```

Показать зарегистрированные ресурсы.

```bash
switchyard run
```

Запустить задачу.

```bash
switchyard explain last
```

Показать последнее решение scheduler.

```bash
switchyard stats
```

Показать статистику.

Интерфейс ещё будет меняться по мере реализации.

## Локальное хранение

Switchyard задуман как local-first приложение.

Поэтому для базовой работы не должен требоваться внешний сервер.

SQLite хорошо подходит для хранения:

* ресурсов;
* состояния;
* истории выполнения;
* usage;
* latency;
* ошибок;
* routing decisions;
* событий.

При этом credentials не должны храниться в базе в открытом виде.

Для секретов лучше использовать системное credential storage, где это возможно.

## Benchmark

Одна из вещей, которую я хочу сделать частью проекта с самого начала, — нормальное сравнение scheduler'ов.

Например, можно создать искусственную среду:

```text
10 ресурсов
1000 задач
разные квоты
разная стоимость
разная задержка
разная вероятность ошибки
разные capabilities
```

А затем прогнать один и тот же набор задач через:

```text
Round Robin
Least Used
Cost Optimized
Quota Optimized
Latency Optimized
Balanced
Switchyard Scheduler
```

И посмотреть:

```text
total cost
average latency
P95 latency
failure rate
successful tasks
quota utilization
fallback count
retry count
```

Это позволяет отвечать на вопросы цифрами, а не ощущениями.

Главный вопрос здесь довольно простой:

> **Действительно ли более сложный scheduler лучше простого?**

Если нет — значит, сложность не нужна.

## Providers

Изначально хочется поддержать несколько разных типов ресурсов, а не просто сделать Switchyard оболочкой над одним API.

Например:

```text
Anthropic
OpenAI
Ollama
```

В дальнейшем можно добавлять другие провайдеры и self-hosted решения.

Главное — чтобы добавление нового provider не требовало менять ядро Switchyard.

Концептуально provider реализует общий интерфейс:

```python
class Provider(Protocol):
    async def execute(...)
    async def health_check(...)
    async def get_usage(...)
```

---

## Безопасность

Проект работает с API credentials, поэтому безопасность здесь не должна появиться «потом».

Основные правила:

* не хранить секреты в Git;
* не хранить credentials в SQLite в открытом виде;
* использовать системное защищённое хранилище;
* не выводить секреты в логи;
* минимизировать объём чувствительных данных, сохраняемых в истории;
* внимательно относиться к debug logging.

---

## Что Switchyard не пытается делать

Switchyard не должен превращаться в огромную платформу «для всего».

Поэтому на первом этапе здесь не будет:

* GUI;
* мобильного приложения;
* Kubernetes-кластера;
* Redis/Kafka только ради того, чтобы они были;
* собственного SaaS;
* биллинга;
* десятков интеграций ради количества;
* ML-scheduler без доказанной необходимости.

Сначала — рабочее ядро.

Потом — эксперименты и измерения.

И только потом — усложнение там, где оно действительно необходимо.

## Идея проекта

В конечном счёте Switchyard — это попытка решить довольно простую проблему:

```text
У нас есть много AI-ресурсов.
У каждого свои возможности и ограничения.
Как эффективно использовать их вместе?
```

Вместо того чтобы вручную решать:

```text
«Этот API сейчас закончился — переключусь на другой»
```

система должна сама видеть доступные ресурсы, понимать состояние каждого из них и принимать решение.

А дальше возникает уже более интересная инженерная задача:

```text
Resources
    ↓
State
    ↓
Policies
    ↓
Scheduler
    ↓
Execution
    ↓
Feedback
    ↓
Better Scheduling
```

Именно вокруг этого цикла строится Switchyard.
