# Switchyard

> Локальная оркестрация разнородных AI-ресурсов.

Switchyard — open-source проект, который помогает работать с несколькими AI-ресурсами как с одной системой.

Под ресурсом здесь может быть что угодно: API провайдера, локальная модель, self-hosted endpoint или несколько доступных ресурсов одного типа.

Идея довольно простая.

Если ресурсов становится несколько, рано или поздно приходится решать, **куда отправить следующую задачу**.

Один ресурс может быть быстрее, другой дешевле. У третьего заканчивается квота, четвёртый временно недоступен, а для конкретной задачи лучше всего подходит пятый.

Можно решать всё это вручную. Можно написать несколько `if` и постепенно добавлять новые условия.

В какой-то момент это уже становится scheduler'ом.

**Switchyard — попытка сделать такой scheduler отдельной, нормальной системой.**

---

## Какую проблему я хочу решить

Представим, что у нас есть несколько ресурсов:

```text
Claude
OpenAI
Ollama
Self-hosted model
...
```

У каждого из них свои характеристики и ограничения:

```text
                Стоимость   Задержка   Квота   Возможности
Claude             $           ↓         80%        +++
OpenAI             $$          ↓↓        40%        +++
Ollama              0          ↓↓↓        ∞          ++
```

Теперь приходит задача.

Она требует определённую модель или capability, желательно должна выполняться быстро, а стоимость не так важна.

Самый простой вариант:

```text
Task → Resource A
```

Но что делать, если `A` недоступен?

А если у него почти закончилась квота?

А если `B` подходит не хуже, но работает в два раза быстрее?

А если эту задачу вообще можно бесплатно выполнить локально?

Получается, что перед каждым запросом нужно принимать решение:

> **какой из доступных ресурсов сейчас лучше всего подходит для этой задачи?**

Именно эту часть я хочу вынести в Switchyard.

---

## Что делает Switchyard

Switchyard собирает ресурсы в единый пул.

Условно:

```text
                       ┌── Resource A
                       ├── Resource B
Task → Switchyard ─────┼── Resource C
                       ├── Resource D
                       └── Resource E
```

Перед выполнением задачи система смотрит на доступные ресурсы и отбрасывает те, которые заведомо не подходят.

После этого scheduler выбирает один из оставшихся ресурсов согласно текущей policy.

Например:

```text
Task:
- нужен большой контекст
- желательно быстро
- стоимость не критична

Resource A
✓ подходит
✓ доступен
✗ высокая задержка

Resource B
✓ подходит
✓ доступен
✓ низкая задержка

Resource C
✗ недостаточно контекста
```

В этом случае выбирается `B`.

После выполнения результат и информация о выполнении могут использоваться для обновления состояния ресурса.

В итоге получается примерно такой цикл:

```text
Task
 ↓
Find candidates
 ↓
Filter
 ↓
Schedule
 ↓
Execute
 ↓
Collect result
 ↓
Update state
```

## Это не просто API Gateway

Здесь есть важное различие.

Обычный gateway в основном решает задачу маршрутизации запроса:

```text
Request → Provider → Response
```

Switchyard интересует немного другая задача:

```text
Workload
   ↓
Requirements
   ↓
Available resources
   ↓
Current state
   ↓
Policy
   ↓
Scheduler
   ↓
Resource
   ↓
Execution
```

То есть вопрос не только в том, **куда отправить запрос**.

Сначала нужно понять, какой ресурс вообще имеет смысл использовать.

Поэтому Switchyard скорее находится между обычным router/gateway и полноценной системой управления ресурсами.

## Resource

В основе проекта лежит понятие `Resource`.

Ресурс — это не просто API key и не просто модель.

У него есть определённые возможности, ограничения и текущее состояние:

```text
Resource
├── provider
├── model
├── capabilities
├── quota
├── rate limits
├── cost
├── latency
├── health
├── priority
└── authentication
```

Например, два ресурса могут использовать одну и ту же модель, но находиться в совершенно разном состоянии:

```text
claude-main
├── quota: 80%
├── latency: 420 ms
└── healthy

claude-secondary
├── quota: 15%
├── latency: 250 ms
└── healthy
```

Для одной задачи выгоднее первый, для другой — второй.

Именно поэтому Switchyard должен работать не только со статической конфигурацией, но и с текущим состоянием ресурсов.

---

## Как выбирается ресурс

Я не хочу начинать проект с какой-нибудь сложной «умной» системы.

Сначала нужны простые baseline-стратегии, с которыми можно сравнивать всё остальное.

Например:

* `Round Robin`
* `Least Used`
* `Quota Optimized`
* `Cost Optimized`
* `Latency Optimized`
* `Quality First`
* `Balanced`

`Round Robin` просто распределяет задачи по очереди.

`Cost Optimized` пытается уменьшить стоимость.

`Latency Optimized` старается выбрать самый быстрый ресурс.

`Quota Optimized` учитывает доступную квоту.

А `Balanced` может учитывать сразу несколько факторов.

Условно:

```text
score =
    reliability
  + quality
  + quota efficiency
  - cost
  - latency
```

Это пока только идея, а не окончательная формула.

Я хочу сначала посмотреть на реальные результаты benchmark'ов и уже потом решать, насколько сложным должен быть scheduler.

## Почему здесь пока нет ML

Потому что ML сам по себе не делает scheduler лучше.

Сначала можно построить вполне нормальный детерминированный алгоритм и проверить его на одинаковом наборе задач.

Например:

```text
Round Robin
      ↓
Balanced
      ↓
Custom Scheduler
```

Если окажется, что простой `Balanced` уже практически оптимален, усложнять систему нет смысла.

Если же история предыдущих запросов действительно помогает предсказывать:

* latency;
* стоимость;
* вероятность ошибки;
* нагрузку;
* эффективность использования квоты;

тогда можно попробовать adaptive scheduler.

То есть потенциальное развитие выглядит примерно так:

```text
Deterministic Scheduler
          ↓
       Benchmark
          ↓
    Find weaknesses
          ↓
      Prediction
          ↓
 Adaptive Scheduler
```

ML здесь должен появиться только в том случае, если эксперименты покажут, что он действительно что-то улучшает.

## Что происходит при ошибках

Выбор ресурса — это только начало.

Даже если scheduler всё сделал правильно, ресурс может:

* вернуть rate limit;
* временно стать недоступным;
* завершиться с ошибкой;
* потерять соединение;
* вернуть ошибку авторизации.

Поэтому выполнение должно уметь восстанавливаться.

Например:

```text
Resource A
    ↓
Rate Limit
    ↓
Backoff
    ↓
Retry
    ↓
не получилось
    ↓
Fallback
    ↓
Resource B
```

При этом retry нужен далеко не всегда.

Если запрос некорректный, отправлять его ещё пять раз бессмысленно.

Поэтому ошибки нужно хотя бы разделять на:

```text
temporary
retryable
fallbackable
fatal
```

## Состояние ресурсов

Чтобы принимать решения, Switchyard должен понимать, что происходит с ресурсами прямо сейчас.

Например:

```text
Resource       Health     Quota     Latency
---------------------------------------------
claude-main    healthy     82%       420 ms
openai-main    healthy     31%       280 ms
ollama-local   healthy      ∞        150 ms
backup         offline      0%         -
```

Часть информации можно получить из конфигурации.

Другую приходится собирать во время работы.

Это состояние впоследствии становится одним из основных источников данных для scheduler.

---

## Объяснимость

Если scheduler выбирает ресурс, хотелось бы понимать почему.

Например:

```text
$ switchyard explain last

Selected: openai-main

Why:
✓ compatible with workload
✓ healthy
✓ sufficient quota
✓ low expected latency
✓ preferred by current policy

Rejected:

claude-main
└─ higher expected cost

ollama-local
└─ insufficient context window
```

Для простого scheduler это удобно.

Для более сложных стратегий это уже практически необходимо.

Я не хочу, чтобы выбор ресурса превращался в ситуацию:

> «Почему он отправил запрос именно туда?»

— «Ну... scheduler так решил».

## Архитектура

Проект пока находится на стадии проектирования, поэтому эта структура ещё может поменяться.

Текущий вариант выглядит примерно так:

```text
src/switchyard/
├── domain/
│   ├── resource.py
│   ├── workload.py
│   ├── quota.py
│   ├── usage.py
│   └── policy.py
│
├── providers/
│   ├── base.py
│   ├── anthropic.py
│   ├── openai.py
│   └── ollama.py
│
├── routing/
│   ├── router.py
│   ├── scheduler.py
│   ├── scoring.py
│   └── policies.py
│
├── quota/
│   ├── tracker.py
│   └── predictors.py
│
├── health/
│   └── monitor.py
│
├── storage/
│   ├── database.py
│   └── repositories.py
│
├── security/
│   └── credentials.py
│
├── cli/
│   └── commands.py
│
└── application/
    └── orchestrator.py
```

Основные части здесь довольно простые.

`domain` — модели предметной области.

`providers` — адаптеры конкретных AI-систем.

`routing` — scheduler и логика выбора.

`health` — состояние ресурсов.

`storage` — локальное состояние и история.

`security` — работа с credentials.

`cli` — пользовательский интерфейс.

## Конфигурация

Конфигурация должна оставаться достаточно простой, чтобы её можно было нормально читать руками.

Например:

```yaml
resources:

  claude-main:
    provider: anthropic
    model: claude-sonnet

  openai-main:
    provider: openai
    model: gpt

  local:
    provider: ollama
    model: qwen

policy:
  strategy: balanced
```

При этом конфигурация не должна превращаться в место, где спрятана вся логика приложения.

## CLI

На первых этапах основным интерфейсом будет CLI.

Например:

```bash
switchyard status
```

Показать состояние ресурсов.

```bash
switchyard resources
```

Показать зарегистрированные ресурсы.

```bash
switchyard run
```

Запустить задачу.

```bash
switchyard explain last
```

Показать последнее решение scheduler.

```bash
switchyard stats
```

Показать статистику.

Команды пока являются предварительными и могут измениться.

## Local-first

Switchyard изначально задуман как локальное приложение.

Для базовой работы не должен требоваться отдельный сервер Switchyard.

Локально можно хранить:

* ресурсы;
* состояние;
* историю выполнения;
* usage;
* latency;
* ошибки;
* routing decisions;
* события.

Для этого на первых этапах достаточно SQLite.

Credentials при этом не должны храниться в базе в открытом виде. Для них лучше использовать системное защищённое хранилище.

---

## Providers

Изначально интересны разные типы ресурсов:

```text
Anthropic
OpenAI
Ollama
self-hosted endpoints
```

Главная цель здесь не собрать как можно больше интеграций.

Гораздо важнее, чтобы добавление нового provider не требовало менять ядро Switchyard.

Концептуально provider будет реализовывать общий интерфейс:

```python
class Provider(Protocol):
    async def execute(...)
    async def health_check(...)
    async def get_usage(...)
```

## Benchmarking

Я хочу, чтобы scheduler можно было не только написать, но и нормально проверить.

Для этого можно создать искусственную среду:

```text
10 resources
1000 workloads

different:
- quotas
- costs
- latency
- failure rates
- capabilities
```

И прогнать одинаковый набор задач через разные стратегии:

```text
Round Robin
Least Used
Cost Optimized
Quota Optimized
Latency Optimized
Balanced
Switchyard Scheduler
```

После этого сравнить:

```text
total cost
average latency
P95 latency
failure rate
successful workloads
quota utilization
fallback count
retry count
```

Меня здесь интересует довольно конкретный вопрос:

> **Действительно ли более сложный scheduler лучше простого?**

Если нет — это тоже полезный результат.

## В двух словах

Если совсем коротко, Switchyard — это попытка ответить на вопрос:

> **У нас есть несколько AI-ресурсов. Как использовать их вместе и при этом не принимать каждое решение вручную?**

Система получает задачу, смотрит на доступные ресурсы, учитывает их текущее состояние и policy, выбирает наиболее подходящий вариант, выполняет работу и сохраняет результат.

```text
Resources
    ↓
State
    ↓
Policy
    ↓
Scheduler
    ↓
Execution
    ↓
Feedback
    ↓
Better decisions
```

Всё остальное — детали вокруг этого цикла.
